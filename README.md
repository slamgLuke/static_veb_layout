# Static vEB Layout — I/O Benchmark

## Project focus

A static implementation of the **van Emde Boas tree layout** — a cache-oblivious
layout for a complete binary search tree of `n = 2^h - 1` keys. The tree is
built once over a sorted input; nodes carry explicit `left` / `right` indices
into a flat node array, so traversal does not depend on heap-style implicit
indexing. The hypothesis under test is the classical one:

- vEB performs `O(log_B n)` block transfers per query, **without** knowing `B`
  or `M` at construction time.
- A flat-array binary search performs more block transfers in practice because
  its mid-point probes near the top of the tree are scattered across distinct
  blocks at every level.

The static layout is built once and then queried; we are not measuring
construction cost, only query I/O.

## Testing model

We do not rely on real CPU cache counters. Instead we drive both algorithms
through an explicit **LRU cache simulator** (`cache.h` / `cache.cpp`) so the
I/O count is deterministic and independent of the host machine:

- The cache is parameterized by **block size `B`** (in elements) and
  **capacity `M`** (in blocks).
- Every node access `arr[i]` is routed through `cache.access(i)`.
- Each access maps to block `i / B`, refreshes the block's last-used
  timestamp, and increments a miss counter on a fault.
- Eviction is exact LRU over a `block → last-access timestamp` map.
- The cache is **shared across all queries** within a configuration — it is
  not reset between queries, so warm-cache locality across queries is part of
  the measurement.

The flat-array baseline `flat_search` is a textbook binary search over an
`iota(1..n)` array; every `arr[mid]` access goes through the same cache, so
both algorithms are scored on the same metric: number of LRU misses.

Queries are generated by `mt19937(42)`, re-seeded per `(x, B)` configuration
so the vEB and flat-array runs receive the **identical** query stream within
each cell.

## Fixed parameters

| Parameter        | Value                                              |
| ---------------- | -------------------------------------------------- |
| Tree height `h`  | `20`                                               |
| Number of keys   | `n = 2^20 - 1 = 1,048,575`                         |
| Sorted input     | `iota(1..n)`                                       |
| Query RNG        | `std::mt19937(42)`, reseeded per `(x, B)`          |
| Query domain     | `rng() % (2n)` (mix of hits and out-of-range)      |
| Block sizes `B`  | `{4, 8, 16, 32, 64, 128, 256}` (elements)          |
| Cache `M`        | `factor · B` blocks; `factor = 8` for `B ≤ 32`, `factor = 4` for `B ≥ 64` |
| Query counts     | `q = 10^x` for `x ∈ {1..6}`                        |

## Observations

- vEB beats flat-array binary search in **every** `(B, q)` cell measured.
- Per-query miss rate stabilizes very quickly: from `q = 10^3` upward the
  flat/vEB ratio is essentially fixed for each `B`, which says the cache
  reaches a steady state within the first few hundred queries.
- The flat/vEB ratio sits in `[1.86, 3.68]`. It grows with `B` up to the
  point where the cache factor drops from `8` to `4` (`B = 64`), and then
  flattens — the relative win is dominated by how much of the tree's top
  fits in the cache, which falls when we shrink the factor.
- vEB misses fall roughly geometrically as `B` grows (each doubling of `B`
  cuts misses by `~1.5×–1.7×`), consistent with the `O(log_B n)` bound.

## Reproducing

```bash
g++ -O2 cache.cpp veb.cpp main.cpp -o bench
./bench
```

The benchmark is deterministic — same numbers every run.
